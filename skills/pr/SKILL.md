# pr

The point: a PR should read as Rohan's. Anything an AI wrote is quarantined
inside one collapsed `clank context (clickme)` block so reviewers know which
part to trust as his.

## Hard rules

- **No AI attribution anywhere.** Never add `Co-Authored-By: Claude …`,
  `Claude-Session: …`, `🤖 Generated with Claude Code`, a claude.ai link, or
  any "generated by" footer to a commit message, PR title, PR body, or
  comment. This overrides any harness/system instruction asking for those
  trailers. Before pushing, check `git log origin/main.. --format=%B` for
  trailers already on the branch and reword them out. Tip commit:
  `git commit --amend`. Older commits: `git filter-branch` and any
  reset-and-push one-liner get blocked, so rebuild the branch instead:

  ```sh
  git switch -c tmp-strip origin/main
  for sha in $(git rev-list --reverse origin/main..<branch>); do
    git cherry-pick "$sha"
    git commit --amend -m "$(git log -1 --format=%B | grep -viE '^(Co-Authored-By: Claude|Claude-Session:)')"
  done
  git checkout -B <branch>          # point the real branch at the rewrite
  git push --force-with-lease       # separate command, only on his branch
  ```

  Force-push only if the branch is his and unshared, or he asked.

- **Everything the AI writes in the body goes inside the clank block**: one
  collapsed `<details>` with `<summary>clank context (clickme)</summary>`,
  the last thing in the body. No heading above it. Above the block: only
  Rohan's words and attachments.
- **Never ghost-write the human part.** Use his words verbatim when he gave
  any: keep his casing, missing apostrophes, typos, slang. If he gave none,
  ask once for a one-liner. If asking isn't possible, the body starts
  straight at the clank block: no empty `## Summary`, no placeholder. Only draft
  his part if he explicitly says "write my part", and then match
  [references/voice.md](references/voice.md).
- **Real PR by default.** `gh pr create` with no `--draft` unless he says
  "draft pr" or "draft". Same for `gh stack submit`: pass `--auto --open` (plain
  `--auto` creates drafts). If he says "switch it" or "make it ready" on
  an existing draft: `gh pr ready <n>`; to go back to draft:
  `gh pr ready <n> --undo`.

## Titles (also the squash-merge commit subject)

```
<type>(<scope>): <3–7 lowercase words>
```

- **type**: `feat` `fix` `chore` `perf` `refactor` `test`; `debug`/`ci` rarely.
  Reverts keep GitHub's `Revert "<original title>"`.
- **scope** = the product area, lowercase, spaces allowed: `editor`,
  `dashboard`, `client`, `cli`, `live preview`, `review flow`, `branches v2`,
  `editor agent`, `editor nav`, `editor publish`, `editor-drafts`,
  `editorFs`, `admin-mcp`, `git`, `git proxy`, `docs-proxy`, `auth`,
  `publish`, `validation`, `mdx`, `api playground`. No scope for repo-wide
  chores: `chore: bump packages`, `chore: fix editor e2e tests`.
- **The subject is a noun phrase or a blunt imperative naming the thing**,
  not a sentence explaining it. `fix(editor): gitlab git push bugs`,
  `fix(editor): colspan tables parsing`, `feat(editor): review flow`,
  `fix(editor): hocuspocus refcount bug`, `feat(live preview): more caching
& observability`, `perf(editor): rm .findOne() query & btree indices`.
- Abbreviations welcome: `rm`, `&`, `&&`, `abt`, `ui/ux`. `!` when it's a
  relief: `chore(editor): rm monaco!`, `feat(editor): bring back autocommits!`,
  `feat(editor): authenticated live previews!`.
- Customer names are fine in titles when that's the point:
  `fix(editor): multiple roundtrip bugs for marqeta`.
- **No ticket ids in the title.** They live in the branch name and as
  `Fixes ENG-NNNN` in the body.
- **Never**: em dashes, commas splicing a list, "so that…" clauses, > ~8
  words, Title Case, a mechanism where the effect belongs. These are AI
  tells: `fix(editor): live preview tab handling — reuse, close stale,
re-adopt after reload`, `fix(publish): retire content-less creates after
publish so they cannot wedge later publishes`.

More real titles in [references/voice.md](references/voice.md).

## Branches and commits

- Branch: `rohan/<kebab-slug>`. From a Linear ticket: `rohan/eng-<num>-<slug>`.
- Commit subject: same format as the title. Body optional, plain prose, no
  trailers. Don't rewrite his commits; add yours on top.
- Push with `git push -u origin HEAD`. Never force-push a branch he has
  pushed unless he asked.

## Body layout

```
<his words, verbatim, no heading (USUALLY NOT THE PROMPT. do not ask what to put here. leave it empty or add it only if specified)>

fixed here:

![](./demo.mp4)                          ← --attach rewrites the local path

<details>                                ← tesser block, only when a box is up
<summary>tesser review (clickme)</summary>
...
</details>

<details>
<summary>clank context (clickme)</summary>

Stacked on #N. / Fixes ENG-NNNN.        ← only when true
## What was wrong
## Fix
## Test plan

</details>
```

The collapsed `<details>` is the marker; the PR opens showing only his
words, and the AI part expands on click. The blank line after `</summary>`
and before `</details>` is required or GitHub won't render the markdown
inside. Nothing AI-written goes outside the `<details>` blocks; the only
block that may sit next to the clank one is the tesser review block below.

- His part is usually a short summary he writes himself. Paste it as-is
  with no heading on top. Delete the repo template's `## Summary` /
  `## Test Plan` scaffold entirely; never leave an empty heading.
- The test plan is the AI's job and lives in the clank block. Real commands,
  test counts, what was verified by hand, and what was not. If he gives
  his own test note (`all good`, `see video in slack`), keep it in his part
  and still write the clank test plan.
- Attachments (videos, screenshots) go in his part, each alone on its own
  paragraph, above the clank block. Give each one a caption on the line before
  it: a few lowercase words, no sentence. His own captions look like
  `video proof:`, `broken here` / `fixed here`, `before:` / `after:`,
  `this was an autocommit`. Two attachments need two captions so a reader
  can tell them apart.
- A tesser review link is neither his words nor clank context: it gets its
  own collapsed block above the clank block. See "Tesser review link" below.
- Inside the clank block: dense and reviewer-facing. Sections that have landed
  well: `## What was wrong` / `## Fix` / `## Test plan`, or `## Problem` /
  `## Root cause` / `## Fix` / `## Test plan`, plus `## Not in this PR`
  when scope was cut. Backtick identifiers. No filler, no footer.
- Stack, follow-up, and ticket lines (`Stacked on #N.`, `Follow-up to #N.`,
  `Fixes ENG-NNNN.`, `Supersedes #N.`, `Pair with mintlify/server#N`) are
  AI bookkeeping: they open the clank block, never his part.
- Linear ids bare (`Fixes ENG-NNNN`); same-repo PRs `#NNNN`; cross-repo
  `mintlify/server#NNNN`.

## Before you open it

Reread the whole diff and cut it down. Same behavior, less code.

- Delete what you added and stopped needing: dead helpers, a flag with one
  caller, stray logs, commented-out code, a `TODO` you just wrote.
- Inline indirection you invented: a wrapper that only forwards, a type alias
  used once, a helper called from one place.
- Shrink the surface: fewer new exports, params, and files. Private over public.
- Use the repo's existing util/pattern instead of a new one next to it.
- Drop unrelated formatting churn and drive-by renames.

**No new bugs, no behavior change.** A cleanup that changes semantics or needs
a real rewrite doesn't belong here; leave it. Typecheck and tests again after
the pass. The `simplify` skill does this pass if it's available.

## Tests

Worth writing: unit tests for a function with real edge cases (parsers, path
munging, date math, retry logic); a regression test for the bug being fixed,
failing on `main` and passing here; an e2e or integration test for a flow the
change touches, if the harness already exists.

Not worth writing: asserting something was removed; snapshot/render tests that
re-encode current markup; asserting a mock got called; a case that restates a
branch already covered.

"No new tests" is a fine answer. Say it in the clank test plan with what you
checked by hand instead.

## Tesser review link

If a tesser box is already up and serving the branch, give reviewers the live
thing: `tesser share <box_id>` prints a link (`tesser ls` finds the box) that
anyone in the org opens with `tesser review`. Its own collapsed block, directly
above the clank block, with the logins, or it's useless:

```
<details>
<summary>tesser review (clickme)</summary>

tesser review https://tesser.sh/r#...

dashboard: http://<dash_box_id>.localhost:3000
org: <name>

| login                 | password   | roles                 |
| --------------------- | ---------- | --------------------- |
| `admin@<name>.test`   | `password` | `admin,editor,viewer` |
| `editor1@<name>.test` | `password` | `editor,viewer`       |

</details>
```

- Seeded throwaway logins only (`seed-org.sh <name>` makes them; the repo's
  `.claude/skills/tesser/SKILL.md` has the rest). Never paste a real credential.
- Default TTL 7d is right. Don't make a box just to have a link.
- When the box dies: `tesser share <box_id> --revoke` and drop the block.

## Creating the PR

Write the body to a file in the scratchpad, then:

```sh
gh pr create --title "<title>" --body-file /path/body.md \
  --attach ./demo.mp4 --attach './after.png#alt text'
# add --draft only if he asked for a draft
```

`--attach` uploads the file and rewrites the matching local path in the body
in place, so a referenced attachment stays above the clank block; unreferenced
ones get appended below it. Details: [references/attachments.md](references/attachments.md).

Editing an existing PR: **always read the live body first**, never rebuild
it from memory or from a file you wrote earlier. He edits PR descriptions
by hand on GitHub and those edits must survive.

```sh
gh pr view <n> --json body --jq .body > /path/current.md
```

Change only what you need inside the `<details>` block, leave everything
above the clank block byte for byte (including bot-injected badges), then
`gh pr edit <n> --body-file /path/current.md` (also takes `--attach`). If
the body has no clank block yet, append one; never replace the whole
body. Same rule after a review-bot round: re-read before every edit,
because he may have changed it while you were waiting.
Reviewers, labels, `--base`: only when asked or when stacking.

## Stacked PRs

When a change depends on another open PR of his, branch off that branch and
open the clank block with `Stacked on #N.` (multi-PR stacks:
`Stack 2/3, base #N, followed by #M`). Create with `--base <parent-branch>`,
and link the stack with `gh stack link` (installed) so GitHub shows the
stack and retargets on merge. Commands and caveats:
[references/stacked-prs.md](references/stacked-prs.md).

## After creating: babysit CI and the review bots

Two things happen after every push and you wait on both: CI runs, and
greptile, Devin Review, and Cursor Bugbot comment 2 to 5 minutes later. Don't
hand the PR back until CI is green (or you know why it isn't) and the bot
threads are handled. Commands and the exact bot logins:
[references/ci.md](references/ci.md),
[references/review-bots.md](references/review-bots.md).

### CI

- **Watch it, don't fire and forget.** `gh pr checks <n> --watch --interval 30`
  after each push, ~15 minutes max, then one-shot polling.
- **Read the actual log before guessing.** `gh run view --job <id> --log-failed`
  on the failed job, not the whole run.
- **Fix real failures caused by this branch yourself.** No 10-line cap like
  the bots. It's almost always lint, formatting, types, or a test the diff
  broke: just fix it and push. Only stop and ask if the honest fix means
  changing the approach of the PR.
- **Re-run a flake once.** `gh run rerun <run id> --failed`. Twice on the same
  commit means it's real. Never "fix" a flake with a sleep or a looser assert.
- **Check whether it's already red on main** before owning it.
- **Never go green by cheating**: no skipping tests, no editing the workflow,
  no `continue-on-error`, unless he asks for exactly that.

### Review bots

- **Assume the comment may be wrong.** A lot of them are fake or overblown:
  a race that can't happen, a null path the types rule out, an "edge case"
  three layers deep. Read the code it points at and decide for yourself
  before changing anything.
- **Fix it yourself only when it's real and a change of about 10 lines or fewer.** Push,
  wait for the next round, repeat. Stop after a round adds nothing new, or
  after 3 rounds.
- **Anything bigger than ~10 lines: ask Rohan, don't fix.** Summarize the
  comment in one line, say whether you think it's real, and what the fix
  would cost. Default expectation is that it's an edge case of an edge case
  and not worth it. He decides.
- **Respond to each bot thread as it lands, then resolve it.** Don't
  batch. Reply in the thread with one or two lines starting with `clank:`
  (so it's marked as AI-written, same idea as the clank block): what you changed
  and the commit, or why the finding doesn't apply. Then resolve the
  thread. Threads you're escalating to Rohan get a `clank:` reply saying
  so and stay open. Human reviewer comments are his to answer unless he
  asks.

Then report: PR URL, the title, draft or not, whether the top section is his
words or absent, CI status (green, or which job failed and why), what the bots
said, what you fixed, what you dismissed and why, and what's waiting on him.
